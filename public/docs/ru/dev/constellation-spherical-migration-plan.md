# План перехода на сферическую геометрию для определителя созвездий

## Зачем это нужно

Текущий определитель созвездий работает в плоской проекции `RA/Dec` (ray-casting в 2D). Для большинства точек это практично, но у такого подхода есть системные ограничения:

- сингулярность на полюсах (`Dec = ±90°`), где `RA` вырождается;
- чувствительность к шву `RA = 0/360`;
- возможные ложные/пропущенные попадания у сложных границ, особенно в высоких широтах;
- необходимость частных fallback-решений для полюсов.

Переход на сферическую геометрию нужен, чтобы:

- убрать классы ошибок, связанные с проекцией;
- корректно и устойчиво обрабатывать полярные области;
- уменьшить количество «спец-случаев» в бизнес-логике;
- повысить доверие к определению созвездий для Astro Frame и тултипов объектов.

## Почему нельзя просто заменить `point-in-polygon`

Прямая замена 2D-проверки на сферическую без изменения представления границ приводит к регрессиям (например, могут ломаться контрольные точки равноденствий/солнцестояний).

Причина: текущий каталог хранит границы в виде полигонов, удобных для плоской проверки. Для корректной сферической проверки требуется явно определённая модель рёбер на сфере и консистентный формат источника границ.

## Цель миграции

Получить строгий и стабильный spherical-конвейер определения созвездия, который:

- сохраняет текущие ожидаемые результаты на контрольных точках;
- корректно работает у полюсов и на шве `RA 0/360`;
- не требует fallback-логики для полюсов в UI/слое Astro Frame.

## Пошаговый план

1. Подготовить слой граничных сегментов (boundary segments)
- Ввести внутренний формат данных, где граница описана как последовательность сегментов с явным типом геометрии.
- Зафиксировать происхождение данных и epoch/frame для трассируемости.

2. Формализовать модель рёбер
- Для каждого типа сегмента определить, как он интерпретируется на сфере.
- Исключить неоднозначность между «плоским ребром в RA/Dec» и «дугой на сфере».

3. Реализовать сферический inside-test
- Векторное представление точки/вершин на единичной сфере.
- Устойчивый критерий принадлежности (с обработкой точки на ребре/вершине).
- Явные `epsilon`-пороги и их документация.

4. Сохранить существующий pipeline эпох
- Оставить текущие преобразования эпох (`EQD -> epoch polygon`) как отдельный слой.
- Менять только геометрию проверки принадлежности.

5. Построить тестовый набор и baseline
- Контрольные точки: равноденствия, солнцестояния, полярные тесты, точки у шва `0/360`.
- Набор «пограничных» точек возле границ созвездий.
- Зафиксировать baseline текущей версии для сравнения.

6. Добавить режим параллельной валидации
- Временно запускать 2D и spherical проверки параллельно (в debug-режиме).
- Логировать расхождения и классифицировать их по типам.

7. Ввести миграционный флаг
- Feature flag для переключения алгоритма.
- По умолчанию оставить текущий путь до прохождения критериев качества.

8. Переключение по готовности
- Включить spherical как основной после прохождения acceptance-критериев.
- Удалить временные fallback/диагностику.

## Acceptance-критерии

- Контрольные точки (включая сезонные маркеры Astro Frame) совпадают с ожидаемыми результатами.
- Полярные точки обрабатываются без ручных fallback-классификаций.
- Отсутствуют регрессии в тултипах объектов и перекрытий.
- Производительность достаточна для интерактивного скраббинга времени.

## Риски

- Неявные особенности исходного формата границ созвездий.
- Чувствительность к выбору `epsilon` около границ.
- Возможные расхождения с внешними инструментами при разных трактовках сегментов.

## Что остаётся без изменений до миграции

- Текущий рабочий 2D-алгоритм в `src/lib/math/constellation.ts`.
- Текущая логика UI/тултипов для `Constellation`.
- Текущие данные каталога созвездий.
