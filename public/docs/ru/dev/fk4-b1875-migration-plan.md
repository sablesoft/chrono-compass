# План перехода на строгую систему FK4 (equinox B1875.0)

## Цель

Перевести определение созвездий для Astro Frame на исторически корректную модель:
- границы созвездий по Делпорту в системе FK4, эпоха/equinox B1875.0;
- преобразования координат без упрощений через современные аппроксимации даты;
- предсказуемая и верифицируемая классификация точек по созвездиям.

## Почему текущая реализация не полностью строгая

Сейчас используется практический путь:
- вычисление точки в of-date экваториальных координатах;
- перевод через современные ротации;
- B1875 задано UTC-датой как аппроксимация.

Это работает стабильно, но не реализует полный исторический контур FK4 (включая специфические нюансы старой системы).

## Что требуется для строгого перехода

1. Ввести явную поддержку кадров и эпох:
- `ICRS/J2000`, `FK5/J2000`, `FK4/B1950`, `FK4/B1875`.

2. Реализовать корректные конверсии между системами:
- precession + frame bias по стандартам ERFA/SOFA;
- особенности FK4 (включая e-terms там, где это требуется выбранной методикой);
- явный контроль `equinox` и `epoch`.

3. Нормализовать формат каталога границ:
- хранить происхождение границ (исходная эпоха/система);
- хранить версию источника;
- добавить служебные поля для верификации.

4. Определить канонический runtime-формат:
- рекомендовано: заранее конвертированные полигоны в `J2000/ICRS`;
- в runtime конвертировать только точку наблюдения в тот же фрейм (или наоборот, но одинаково для всех).

5. Улучшить геометрию проверки попадания:
- сохранить текущий RA/Dec-полигон как базовый вариант;
- добавить строгий spherical fallback для сложных зон (полюса/шов 0-360);
- формализовать правило для точки на границе.

6. Подготовить эталонную верификацию:
- сравнение с `astropy/ERFA` на наборе дат (прошлое/настоящее/будущее);
- отдельный набор точек близко к границам;
- отчёт о расхождениях (угл.сек + доля смены созвездия).

## Рекомендуемый путь внедрения

1. **Оффлайн-конвертер (эталон)**
- сделать скрипт (Python + Astropy), который:
  - читает исходные границы Delporte;
  - приводит их к строгому `FK4 B1875.0`;
  - конвертирует в целевой runtime-фрейм (`ICRS/J2000`);
  - экспортирует JSON/TS-объекты.

2. **Заморозка каталога**
- сохранить сгенерированные полигоны в `src/lib/catalog/objects/constellations`;
- добавить метаданные версии генерации/источника.

3. **Интеграция в runtime**
- использовать единый фрейм для точки и полигонов;
- убрать аппроксимационные участки, где они больше не нужны.

4. **Тесты и регрессия**
- unit-тесты для конвертаций;
- snapshot-тесты классификации граничных точек;
- контроль производительности на интерактивном скраббинге времени.

## Критерии готовности

- Для контрольного набора дат классификация совпадает с эталоном (`astropy/ERFA`) в рамках принятых допусков.
- Расхождение угловых координат документировано и не превышает целевой порог.
- Поведение на границах (tie-break) формально описано и стабильно в тестах.
- Документация содержит трассируемость: источник данных, модель, версия генерации.

## Риски

- Различия трактовки FK4/FK5 в разных библиотеках.
- Нестабильность на границах при разных tie-break правилах.
- Рост сложности пайплайна генерации каталога.

## Что можно оставить как есть до миграции

- Текущий runtime-поиск по полигонам.
- Текущий UI/тултипы `Constellation`.
- Текущую структуру `constellation` объектов (дополнив служебными метаданными позднее).
