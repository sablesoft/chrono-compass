# Архитектура датасетов

Этот документ описывает **архитектуру вычислений на основе датасетов**, используемую в Chrono Compass.

Ключевая идея проста:

> **Все тяжёлые астрономические вычисления выполняются заранее.**
> Браузер никогда не считает реальные эфемериды. Он только *визуализирует* заранее вычисленные циклы.

Это позволяет приложению оставаться:

* полностью статичным,
* офлайн‑совместимым (PWA),
* лёгким (без backend и runtime‑движков),
* предсказуемым и хорошо отлаживаемым.

---

## Общая концепция

Каждый тип колеса (Compass, Horizon, Synod, Range и т.д.) имеет собственный алгоритм вычисления **вне браузера**.

Результат работы такого алгоритма — **датасет**, который:

* состоит из множества *циклов*,
* каждый цикл представлен **16 спицами**,
* каждая спица соответствует конкретному событию или опорному моменту данного цикла.

Во время работы приложения браузер:

* выбирает нужный чанк датасета по времени,
* выбирает нужный цикл внутри этого чанка,
* интерполирует *только между спицами* для визуализации.

Никаких астрономических вычислений на стороне клиента не происходит.

---

## Колёса, не покрываемые датасетами

Вычисления на основе датасетов намеренно не применяются к колёсам типов Compass и Horizon, поскольку они зависят от непрерывного пространства положения наблюдателя (широта и долгота) и представляют собой локальные проекции, а не глобальные циклы.

Эти колёса вычисляются алгоритмически в рантайме и в будущем могут использовать вспомогательные предварительно вычисленные данные, но не полноценные датасеты циклов.

---

## Почему именно 16 спиц

Chrono Compass использует фиксированную **16‑спицевую структуру** для всех типов колёс.

Это даёт:

* единый визуальный язык для всех колёс,
* предсказуемую навигацию (E+, E−, дома, спицы),
* сильное сжатие данных по сравнению с непрерывными временными рядами.

17‑я спица (E+) **не хранится**.
Она неявно является первой спицей следующего цикла.

---

## Гранулярность датасетов

Датасеты разбиваются не по календарным годам, а по **группам полных циклов**.

При этом **каждый чанк датасета всё равно имеет точные временные границы**, потому что:

* циклы могут быть асимметричными,
* длины циклов могут меняться со временем,
* выбор чанка всегда начинается от абсолютного момента времени.

Следовательно:

* чанк выбирается по времени (`startTs ≤ t < endTs`),
* циклы — это лишь внутренняя структура чанка.

---

## Расположение файлов датасетов

Все датасеты хранятся в статической папке `public`:

```
public/datasets/{wheelType}/{tupleId}/{chunkId}.json
```

Примеры:

```
public/datasets/synod/earth_sun_moon/1800-1810.json
public/datasets/range/earth_mars/1900-1950.json
```

Эти файлы отдаются как статические ресурсы и подгружаются по требованию.

---

## Структура датасета (минимальный скелет)

Каждый файл датасета — это обычный JSON‑объект со следующей обязательной структурой:

```ts
{
  type: string,          // тип колеса (для дебага и валидации)
  tuple: string[],       // упорядоченный кортеж тел (для дебага и валидации)

  startTs: number,       // совпадает с cycles[0].spokes[0].ts
  endTs: number,         // виртуальная спица 16 последнего цикла

  default: boolean,      // загружать ли этот датасет сразу

  cycles: [
    {
      spokes: [
        { ts: number, meta?: object }, // 16 элементов
        ...
      ]
    },
    ...
  ]
}
```

### Примечания

* `startTs` **обязан совпадать** с моментом первой спицы первого цикла.
* `endTs` **обязан быть строго больше**, чем момент последней спицы последнего цикла.
* Каждый цикл содержит **ровно 16 спиц**.
* Временные метки спиц внутри цикла должны строго возрастать.
* Поле `meta` зависит от типа колеса и не интерпретируется загрузчиком датасетов.

---

## Метаданные спиц

Каждая спица может содержать дополнительные метаданные, специфичные для типа колеса.

Примеры:

* Compass: азимут, высота, флаги видимости
* Horizon: высота, флаги восхода/захода
* Synod / Channel: угловое расстояние
* Bind / Range: расстояние
* Season / Plato: параметры ориентации оси
* Nodal: долгота узлов или ориентация плоскости

Браузер **не интерпретирует** эти данные.
Они напрямую передаются логике отрисовки соответствующего колеса.

---

## Манифест датасетов

Чтобы избежать ручного сопровождения, Chrono Compass использует **автоматически генерируемый манифест датасетов**.

Манифест создаётся на этапе сборки путём сканирования папки с датасетами.

Расположение:

```
public/datasets/manifest.json
```

---

## Назначение манифеста

Манифест:

* перечисляет все доступные чанки датасетов,
* валидирует консистентность датасетов на этапе сборки,
* обеспечивает ленивую загрузку по времени,
* позволяет заранее загрузить датасеты по умолчанию.

Разработчик **никогда не редактирует манифест вручную**.
Он просто добавляет или обновляет файлы датасетов.

---

## Структура манифеста (упрощённая)

```ts
{
  version: number,
  generatedAt: string,

  // Предварительно вычисленный список чанков,
  // которые нужно загрузить сразу при старте приложения
  defaults: [
    {
      wheelType: string,
      tupleId: string,
      chunkId: string,
      url: string,
      startTs: number,
      endTs: number
    }
  ],

  datasets: {
    [wheelType: string]: {
      [tupleId: string]: [
        {
          id: string,          // идентификатор чанка (например "1800-1810")
          url: string,         // публичный URL файла датасета
          startTs: number,
          endTs: number,
          default: boolean     // признак eager‑загрузки
        }
      ]
    }
  }
}
```

Чанки внутри каждой группы `(wheelType, tupleId)` отсортированы по времени.

Поле `defaults` является денормализованным индексом, чтобы браузеру не приходилось сканировать весь манифест.

---

## Датасеты по умолчанию и ленивая загрузка

Каждый чанк датасета объявляет флаг `default`.

* `default: true`

    * загружается сразу при старте приложения,
    * используется для базовых и часто применяемых колёс,
    * гарантирует мгновенную доступность.

* `default: false`

    * загружается лениво по требованию,
    * подгружается только при необходимости,
    * кэшируется для офлайн‑использования.

Это позволяет приложению быстро стартовать и при этом поддерживать большие исторические диапазоны.

---

## Поведение в рантайме (браузер)

Во время работы приложение:

1. Загружает `manifest.json`.
2. Сразу загружает все чанки, перечисленные в `manifest.defaults`.
3. При взаимодействии пользователя:

    * определяет `(wheelType, tupleId, selectedTs)`
    * выбирает подходящий чанк по времени
    * загружает его, если он ещё не закэширован
4. Отрисовывает колесо, используя только интерполяцию между спицами.

Если пользователь офлайн и нужных данных нет:

* интерфейс сообщает, что требуются дополнительные данные,
* запрос ставится в очередь,
* данные автоматически загружаются при восстановлении сети.

---

## Кэширование датасетов и инвалидация

Датасеты считаются **иммутабельными артефактами**.

Любое изменение датасета приводит к появлению **нового версионированного URL** (через версию или хэш содержимого).
Кэш браузера всегда ключуется именно по URL.

### Стратегия кэширования

* Все датасеты кэшируются в отдельном пространстве кэша (например `cc-datasets`).
* Датасет попадает в кэш при первой успешной загрузке.
* Кэш используется между сессиями и в офлайн‑режиме.

### Обновление манифеста

При загрузке нового `manifest.json`:

* приложение сравнивает версию манифеста с ранее загруженной,
* изменение версии означает, что набор доступных датасетов мог измениться.

**Важно:**
Изменение версии манифеста **не приводит к перезагрузке всех датасетов**.
Повторно загружаются только те датасеты, у которых изменился URL.

### Сборка мусора в кэше

Чтобы предотвратить неограниченный рост кэша, приложение выполняет **best‑effort очистку кэша** после обновления манифеста.

Процедура очистки:

1. Формируется множество всех URL датасетов, упомянутых в текущем манифесте
   (включая `defaults` и обычные чанки).
2. Выполняется проход по всем закэшированным датасетам.
3. Любой закэшированный файл, URL которого **отсутствует** в текущем манифесте, удаляется.

Таким образом удаляются устаревшие версии датасетов.

### Правила безопасности

* Очистка кэша не должна удалять датасеты, которые в данный момент используются интерфейсом.
* Очистка может быть отложена (например, выполнена в idle‑режиме или при следующем запуске).
* Сбой очистки кэша никогда не должен ломать работу приложения.

---

## Архитектурные преимущества

Данная архитектура обеспечивает:

* **Отсутствие астрономических вычислений в браузере**
* **Чёткое разделение физики и UI**
* **Детерминированные и воспроизводимые колёса**
* **Офлайн‑ориентированное поведение**
* **Минимальные расходы на хостинг** (чисто статические файлы)

Самое главное:

> Браузер становится *навигационным инструментом*, а не симулятором.

---

## Будущие расширения

Система датасетов изначально спроектирована как расширяемая:

* в будущем возможны бинарные форматы для уменьшения размера,
* возможна поддержка нескольких версий датасетов,
* более точные датасеты могут прозрачно заменять грубые,
* внешние генераторы (Skyfield, SPICE) могут быть добавлены без изменений фронтенда.

Все подобные изменения происходят **только на этапе сборки** и не затрагивают архитектуру рантайма.
